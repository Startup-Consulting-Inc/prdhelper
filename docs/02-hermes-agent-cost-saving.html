The $30 bill that should have been $7

A forensic audit of 936 OpenRouter calls over 20 days. Where the money leaked, how to plug it, and what your production AI agent is probably doing wrong too.

By Jaehee Song April 22, 2026 15 min read

WHAT YOU'LL GET FROM THIS POST

Three concrete moves that took my AI agent's running cost from $30.66 over 20 days down to a projected $6.84 — a 78% reduction — without dropping any capability. The moves are model routing, provider selection, and prompt caching. None of them require writing new model code. All of them apply to any agent built on OpenRouter or a similar gateway.

I run a multi-agent stack called Hermes Agent. It manages five web properties — SEO snapshots, AI citation monitoring, automated Telegram reports, the whole operation. It ticks along in the background, makes a few hundred API calls a day, and sends me a nice Monday morning summary. It's useful. And for most of April, it was quietly bleeding money.

The bleeding was gentle at first. A few cents here, a few dollars there. Then on April 8 I ran an experiment with Claude Opus 4.6 that cost me $19.81 in a single afternoon — roughly two-thirds of my entire 20-day spend. That got my attention. When I sat down to analyze the full dataset of 936 generations, what I found wasn't one expensive mistake. It was three separate cost leaks, each small on its own, adding up to real money.

Here's what the 20 days looked like. The spike on April 8 is the Opus experiment. The steady high-volume days after April 18 are normal Hermes Agent operation — and they have their own problems.

02Where the money went (the uncomfortable part)

Here's the thing I wish I'd built into my monitoring from day one: a cost breakdown by model. When I finally looked at it, the answer was almost comic.

The cost attribution that should have stopped me a week earlier

Share of requests vs share of cost, by model

Claude Opus 4.6 handled 10% of the requests and ate 65% of the budget. Kimi K2.5 handled 81% of requests for 32% of the cost. One of these is pulling its weight. One of them is not.

Kimi K2.5 is doing the work. It's handling 757 of my 936 calls at an average cost of $0.013 per call. It's slow-ish — about 34 seconds average latency — but these are background jobs, so latency doesn't matter. Kimi costs me $0.311 per million blended tokens on its best provider. That's genuinely cheap.

Claude Opus 4.6 handled 91 calls at an average of $0.22 per call. That's seventeen times more per call than Kimi. And here's where it gets painful: those 91 calls were all on April 8, all going through Hermes Agent, and all behaving exactly like Kimi calls — 60K-token inputs, ~340-token outputs, mostly tool_calls. I wasn't using Opus for its reasoning. I was using it as an expensive Kimi substitute.

THE CORE MISTAKE

I used Opus 4.6 for a routine agent tool-loop. The "big thoughtful model" setting is good for synthesis, hard debugging, final report generation — tasks where one extra iteration of quality compounds through the rest of the pipeline. It's catastrophically wasteful for function-call loops where the model is just emitting structured JSON to call the next tool. Use a sledgehammer to crack a walnut enough times and you'll break your foot.

03The provider routing problem (same model, wildly different rates)

Here's something people don't talk about enough. OpenRouter doesn't just give you access to models — it gives you access to providers who host those models. For an open-weight model like Kimi K2.5, there are a dozen providers competing on price, latency, and quantization. You can pick, or you can let OpenRouter's default router pick for you.

THE LESSON FROM THIS ONE TABLE

If you're using OpenRouter for open-weight models, set a provider preference explicitly. OpenRouter's default router is optimizing for availability, not for your bill. One line of config changes everything.

04Three moves that cut the bill by 78%

Now we get to the practical part. Here are the three moves, in order of dollar impact. Each one took less than an hour to implement.

Move 1 · largest impact

Stop using Claude Opus for agent tool loops

saves $19.05

The problem: All 91 Opus calls were tool-call loops with tiny outputs. Average prompt: 59,544 tokens. Average completion: 339 tokens. That's a classic agent pattern — big context, small response — which is exactly what cheap models do well.

The fix: Route Opus only to tasks where its reasoning genuinely differentiates — complex planning, final synthesis, hard debugging. Never to function-call loops. In Hermes Agent, that meant moving one line in the router config:

route_rules = {
  "tool_loop": "moonshotai/kimi-k2.5",      # cheap, good enough
  "synthesis": "anthropic/claude-opus-4.7",  # reserve for this
  "simple_query": "google/gemini-3-flash",   # even cheaper
}

Projected savings: $19.05 on the same workload. The math: 5.4M Opus input tokens at $5/MTok becomes 5.4M Kimi input tokens at roughly $0.14/MTok — and Kimi produced equivalent tool-call outputs in my spot checks.

Move 2 · easy win

Pin Kimi to SiliconFlow, exclude the slow providers

saves $4.77

The problem: 598 of my Kimi calls were routed through Chutes at $0.311 per million blended tokens. SiliconFlow charges $0.139 for the same model. Same output. Faster. No reason not to use it.

The fix: Add provider preferences in the OpenRouter request. This is the one line of config I wish I'd written on day one:

{
  "model": "moonshotai/kimi-k2.5-0127",
  "provider": {
    "order": ["SiliconFlow", "Inceptron", "Chutes"],
    "ignore": ["Phala", "Together", "Novita", "Moonshot AI", "Parasail"],
    "allow_fallbacks": true
  }
}

Why ignore the bottom four? Those providers routed 8 of my requests, and they cost 5–15 times the median rate while averaging multi-minute latency. Excluding them prevents OpenRouter from ever sending your request there, even during failover. The order array ensures SiliconFlow gets tried first, Inceptron second, Chutes third. You keep your redundancy while hitting the cheapest path by default.

Projected savings: $4.77 over the 20-day window. At scale (say, 30,000 calls a month), this one config line saves roughly $7 per month per thousand calls.

Move 3 · compounding over time

Restructure prompts to push cache hit rate from 48% to 70%

saves $1.48+

The problem: My Hermes Agent sends a median of 34K tokens of prompt per call, with a p99 of 122K. A lot of that is the same system prompt and tool definitions, repeated across 822 requests. I was getting 48.5% cache hits — which is decent, but there's more on the table.

The fix: Prompt structure matters for caching. The cache works on prefix stability. Anything that changes at the top of the prompt breaks the cache for everything after it. So:

  • Move stable content to the top. System prompt → tool schemas → persistent context → then the variable task input. Not the other way around.
  • Don't inject timestamps near the top. A line like "Today is 2026-04-22 14:31:07 UTC" in your system prompt breaks the cache every second. If you need the time, put it at the bottom of the user message.
  • Share prefixes across related skills. If my SEO-snapshot, AI-citation, and GSC skills share 80% of their system prompt, I pull that into one shared prefix. All three benefit from the same cache entry.

Projected savings: $1.48 on top of the existing $3.33 in Kimi cache savings. More importantly, this scales with your traffic — the more calls you make, the more this compounds.

The cache hit rate that varied by which app was calling

Here's something I almost missed until I sliced the data differently. Cache hit rate isn't a property of the model — it's a property of how each app sends requests. When I grouped by app name, the spread told a story I wasn't expecting.

Cache hit rate by application

Three apps, three different caching stories

Hermes Agent does okay at 48.7%. PRD Helper is slightly lower at 42.5%. The unlabeled requests — mostly my deep-researcher running without an app tag — come in at 28.6%, but the Opus subset within that bucket hit exactly 0%.

The unlabeled Opus calls were the painful discovery. 18 Opus requests, every single one at 0% cache hit rate. Each shipped 87K–100K prompt tokens of fresh context. That's 15-plus calls in a single research loop, with no cache markers, re-paying full input price on tokens that had appeared in the previous call 30 seconds earlier.

THE MATH ON THE MISSED CACHE

18 unlabeled Opus requests × ~90K prompt tokens × 0% cache hits × $5/MTok input = roughly $8.10 in fresh-read charges that should have been ~$0.81 with caching enabled. The per-token gap between cached and uncached reads on Opus is 10×. When you miss the cache, you don't just lose a small discount — you pay an order of magnitude more for the same bytes.

Every app in your system should get its own app name in the OpenRouter request header. Without it, you can't diagnose which workflow is the one leaking. Mine was hiding under "unknown" — which is why it took a CSV export to find.

05Prompt bloat: the silent 300-to-1 leak

This one surprised me when I sorted the dataset by prompt size. My top 50 most expensive Kimi calls sent 120K+ prompt tokens to get back 30 to 400 completion tokens. That's a 300-to-1 ratio. I was paying to ship a cargo container to deliver a postcard.

Prompt size vs completion size

Each dot is one request · dot size represents cost

The cluster in the top-left corner is agent-loop bloat: massive prompts, tiny responses. Eight of those calls fired within 20 minutes on April 18 — the same conversation history being re-sent on every single turn.

What was in those 120K tokens? Looking at the timestamps, the pattern was unmistakable: the same conversation history, the same file contents, the same accumulated tool results, re-appended turn after turn. By the 8th iteration of a research loop, the prompt had collected every previous tool call, every previous assistant response, and every previous user input. Nothing was being pruned. Nothing was being summarized. The agent was just dragging its entire history forward, paying for every token of it, every time.

Three techniques to shrink the bloat

Technique 1 · best ROI

Rolling summaries instead of full conversation history

After every N turns (I use 5), ask the model to summarize the conversation so far. Replace the full message list with [system, summary, last_3_turns]. This caps prompt growth regardless of how long the session runs.

if turn_count % 5 == 0 and turn_count > 0:
    summary = summarize(messages[1:-6])  # everything except system + last 3 turns
    messages = [messages[0], summary_msg(summary), *messages[-6:]]
Technique 2 · for document-heavy agents

Reference by ID, not by content

If your agent is working with files, wiki pages, or documents, pass a reference ID and a one-line description instead of embedding the full text. Let the model ask for specific chunks if it needs them. This is how RAG systems work, and it cuts prompt size by 80% or more on content-heavy agents.

Technique 3 · the safety net

Hard context ceiling

Configure your agent client to error out (or auto-summarize) when the prompt exceeds a threshold. I've set mine to 50K tokens for Kimi agent loops. If a task genuinely needs more than that, it should be split into sub-tasks — not crammed into one megaprompt. The ceiling forces the architectural conversation you'd otherwise keep putting off.

06Choosing the right model for the right job

The $19 Opus mistake on April 8 wasn't really about Opus being expensive. It was about using a frontier reasoning model for a task that didn't need frontier reasoning. If I'm honest, most of what Hermes Agent does — tool calls, file reads, short summaries — can be handled by models much further down the cost curve without any quality loss.

Here's the mental model I'm adopting, based on what the token shape actually tells me about each task:

Model Blended $/MTok Avg latency Best for
Claude Opus 4.7 $3.64 7.8s Frontier reasoning, novel problems, final synthesis where quality compounds
Claude Sonnet 4.6 $0.80 ~2s Tool use, synthesis loops, coding — most agent work most of the time
Kimi K2.5 $0.14 22s High-volume background agents, long-context processing
Gemini 3 Flash $0.57 3.8s Quick summaries, drafts, vision tasks, low-stakes work

MY NEW ROUTING RULE

  • Frontier reasoning or final synthesis where quality matters most → Opus
  • Tool loops, coding, research synthesis, most production agent work → Sonnet
  • High-volume background chatter, long-context batch work → Kimi on SiliconFlow
  • Drafts, quick summaries, cheap vision → Gemini Flash

The thing I'd emphasize: Sonnet is the right default for agent tool loops, not Opus. Opus is the right choice when you need the one-shot answer to be exceptional — final synthesis at the end of a long pipeline, hard debugging, complex planning. For everything in between, Sonnet is roughly 20% of Opus's cost at similar quality on most tasks.

08The two smaller things worth fixing

Cap your output tokens

On April 22, two of my Gemini 2.5 Flash calls hit the 65,535-token maximum output length. Together they cost 33 cents on what should have been two-cent calls. Most likely a retry loop or a missing stop condition in the agent logic. Whenever I see a completion that hits a round number like 65,535, 4,096, or 2,000, it's almost always a configuration problem — not a task that legitimately needed that much output.

The fix is simple: set max_tokens to something reasonable for your task. If your agent is emitting a tool call, 512 tokens is plenty. If it's writing a summary, 1,500. If it hits the cap, you'll see finish_reason: "length" in the response and you can decide whether to retry with a bigger budget or rethink the prompt.

A MONITORING TIP

Add an alert for any call where finish_reason == "length". Three of those in 20 days is borderline. Thirty of those in a day is a bug hemorrhaging money.

Check your cache utilization weekly

Cache hit rate is the single most sensitive cost metric you have. If you see it drop from 48% to 20% suddenly, something changed in your prompt structure — maybe someone added a timestamp, maybe someone reordered the system prompt, maybe your tool schemas got regenerated with different formatting. These changes don't look like bugs. They look like housekeeping. But they can double your bill overnight.

10What I'm leaving alone

Not everything in the audit needed fixing. It's worth calling out what was working, because the temptation with this kind of analysis is to optimize every byte, and that's how you end up spending five hours saving 40 cents.

PRD Helper stays exactly as it is. 41 requests, $0.64 total, all on Gemini 2.5 Flash, sub-second latency, healthy prompt-to-completion ratio. Nothing to change here.

Kimi on Chutes, while suboptimal, isn't broken. The agent's logic is sound; it's just running on the wrong provider. That's a routing config fix, not a code fix. I don't need to rebuild anything.

Gemini 2.5 Flash for document processing stays. It's fast, cheap, and handles the quick-summary tasks I throw at it. Even with the two 65K-token runaway completions I need to investigate, the overall cost profile is excellent.

The goal isn't to optimize every token. It's to stop paying three times more than necessary for the same output.

11What this means for your agent

My Hermes Agent is small. A few hundred dollars a month at the high end. But the patterns that caused the leaks here — using the wrong model for the wrong task, letting the router pick providers, ignoring cache utilization, not capping output — those patterns don't scale down. They scale up.

Looking back, the $18+ of waste in this dataset came from four specific anti-patterns, and they're the same four anti-patterns I'd bet are hiding in most production agent deployments:

  1. Provider indifference. Letting OpenRouter pick the default when a 2× cheaper option exists one config line away.
  2. Cache blindness. Sending 90K-token prompts 15 times in a row without ever marking the static context for caching.
  3. Model overkill. Using Opus for agent tool loops that Sonnet or Kimi would handle equivalently at 5-26× lower cost.
  4. Unbounded context. Letting conversation history accumulate until a single turn costs more than an entire Sonnet session would have.

If you're running a production agent and your bill is $500 a month, these same four patterns probably save you $350 once you address them. If your bill is $5,000, they probably save you $3,500. The math is linear because the mistakes are structural.

The agent itself is fine. The logic works. The outputs are good. What was broken was the infrastructure around the agent — the model choice, the provider routing, the prompt structure. None of that shows up in your product's feature list, but all of it shows up in your monthly statement.

If you run agents through OpenRouter, go do this audit. Export your activity CSV. Group by provider. Sort by prompt tokens. Look for zero-cache requests. The waste is probably there, and it's probably bigger than you think.
